# Current behavior requirements and implementation status

This is the entry point for the current live behavior contract. Detailed specifications own the rules linked below; this overview makes platform differences and implementation gaps explicit. Demo fixtures and standalone legacy libraries are not alternate live modes.

The [architecture contract](../development/architecture.md) defines the reconstruction boundaries and acceptance. Latest accepted behavior takes precedence over obsolete implementation notes.

## Platform execution and notice delivery

These are current implementation choices, not claims that a platform requires this architecture in every integration. The [SOOP public-documentation recheck](../reference/soop.md#server-side-support-recheck--2026-10-05) found browser SDK support but no documented official server chat transport; the browser path remains in use.

| Platform | Receiver location                                                                          | Participation notice delivery                                                                                                                                                      | Admin tab dependency                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| SOOP     | Official Chat SDK in the admin browser; events go to the app server for consent filtering. | Browser SDK sends server-issued fixed notices. A matching authenticated broadcaster MESSAGE echo confirms delivery. Manual delivery confirmation is disabled.                      | The connected admin tab must remain open for receipt and sending. Browser connections to SOOP are expected in this implementation. |
| YouTube  | Server, using the official REST/gRPC receiver.                                             | Server OAuth sender uses `liveChatMessages.insert`; matching response data confirms delivery of one short notice. Manual confirmation is disabled.                                 | No open admin tab is required after authentication while the server receiver runs.                                                 |
| CHZZK    | Server with an isolated Socket.IO 2 worker.                                                | Server OAuth sender uses the official Chat API. The single notice (at most 100 characters) must return a message ID before delivery is confirmed. Manual confirmation is disabled. | No open admin tab is required after authentication while the server receiver runs.                                                 |

See [live setup](../operations/setup.md) for credentials, broadcaster identity, reviewed permissions, allowed rates and delivery procedures. Authentication is not viewer consent. Confirmed guidance is shared among recently observed viewers in the same room and persists across restarts of the current broadcast. Ambiguous remote writes can be retried; delivery tracking is not an exactly-once guarantee.

## Explicit boundaries and remaining acceptance

- Video and audio start from their configured sources without separate enable flags. Mask acknowledgement and manually authored personas are not prerequisites. Historical implementation records must not be used to reintroduce those gates.
- Automatic persona composition does not clone real viewers or use their histories. Legacy authoring APIs and library tests do not establish live availability.
- Age is self-declared, not verified. No guardian-consent verification workflow exists.
- Anonymous summaries use local fixed categories with a minimum distinct-account threshold. Their tests do not certify legal anonymity.
- Session deletion does not perform provider deletion, video editing or deletion of copies. Rights handling tracks separate work; automatic VOD editing and exhaustive per-viewer video indexing are not implemented requirements.
- Real platform permissions, event ordering, notice delivery, provider/account eligibility and external deletion remain operational acceptance. See [privacy acceptance](participation.md#acceptance-and-operational-checks).

## Keeping this contract current

When requirements change, update this overview and the owning detailed specification together, identify implementation gaps in the owning specification, and record checks actually run in the commit description. Explicit accepted requirement changes supersede older requirements; an implementation limitation does not silently redefine the desired behavior. Private source material stays private: preserve its accepted behavior here, not a broken link to an unavailable file. Dated research and verification are evidence for their stated revision and scope, not current acceptance.

The explicit [operator-reviewed test configuration](participation.md#operator-reviewed-test-configuration) can defer descriptive profile metadata during reviewed testing. Viewer consent, withdrawal, channel approval, model compatibility and actual notice limits remain required.

[Single-step consent](participation.md#participation-and-guidance) is the normal flow, without a separate test mode. Broadcast accounts are excluded and AI uses normal participation probabilities.
