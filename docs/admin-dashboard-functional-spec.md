# 관리자 운영 대시보드 기능 명세

**문서 버전:** 1.3

**코드 대조일:** 2026-10-05

**상태:** 목표 요구사항 — 일부 구현, 아래 차이 표 참조

**대상:** Mixed Chat Studio의 관리자 화면과 운영 상태 API

이 문서는 방송 중 시스템 상태와 운영 제어를 빠르게 확인하기 위한 관리자 화면의 우선순위와 필수 동작을 정의한다. 페르소나 작성 화면, 연결 설정 화면, AI 상세 정보보다 이 문서의 최상단 운영 대시보드 요구가 먼저 적용된다. 현재 [AI Viewer Persona System 구현 명세](./ai-viewer-persona-system-spec.md)의 라이브 운영 화면 요구를 보완한다.

`MUST`는 필수 요구, `SHOULD`는 특별한 이유가 없으면 따라야 하는 권장 요구다.

## 현재 구현과 요구사항의 차이

아래 본문의 MUST/SHOULD는 목표 계약이며 현재 동작을 보장하지 않는다. 근거는 [관리자 UI](../apps/web/src/main.tsx), [서버 API와 진입점](../apps/server/app.ts), [재시작 처리](../apps/server/main.ts), [저장소](../packages/storage.ts)다. 상단 대시보드는 [operations-dashboard.tsx](../apps/web/src/operations-dashboard.tsx)에 구현되어 있다.

`GET /api/admin/status`는 `generatedAt`(응답 생성 epoch ms)과 `originsRevealed`(현재 스트림 공개 여부)를 추가로 제공한다. 글로벌 `POST /api/admin/ai/start`는 준비 검사 후 현재 live 페르소나가 비무장이라면 재무장한다. `POST /api/admin/reveal`은 생성과 live 페르소나를 함께 중지해 공개 후 재시작 의도가 남지 않게 한다. 공개는 현재 세션에서 되돌리는 토글이 아니다. 버튼은 `AI 채팅에 ‘AI 생성’ 표시하기`로 동작을 명시하고, 공개 후에는 버튼 대신 `AI 채팅에 ‘AI 생성’ 표시 중` 상태 문구를 보여준다.

## 1. 제품 원칙

1. 운영자는 페이지를 열자마자 AI가 실행 중인지, 방송 입력과 채팅 연결이 준비됐는지, 개인정보 보호와 안내 토글이 어떤 상태인지 한눈에 알아야 한다.
2. 대시보드는 설정 양식이 아니라 실시간 운영 화면이다. 상태를 읽기 위해 여러 카드를 찾아다니거나 로그를 해석하게 해서는 안 된다.
3. 문제 원인, 영향받는 입력, 가능한 조치를 같은 화면에서 보여준다.
4. 상태가 불명확하거나 오래됐으면 정상으로 표시하지 않는다. `확인 중`, `알 수 없음`, `오래된 상태`로 구분한다.
5. AI와 입력 수집은 별도 상태다. AI를 중지해도 수집 채팅은 계속될 수 있고, 필수 입력이 불완전하면 AI를 시작할 수 없다.
6. 동의 전 시청자 채팅 원문은 저장·표시·모델 입력으로 보내지 않는다. 개인정보 보호 규칙은 편의 기능이나 대시보드 토글로 우회할 수 없다.

## 2. 첫 화면 배치

관리자 화면의 첫 운영 영역은 반드시 **통합 상태·제어 대시보드**다. 페르소나 스튜디오, 브리프 작성, 연결 상세, 사용량 분석은 이 영역 아래에 둔다. 로그인 화면을 제외한 관리자 첫 화면에서 대시보드보다 먼저 긴 설명, 폼, 설정 카드가 나타나면 안 된다.

```text
┌ 방송/세션 상태 ──────────────────────────────────────────────┐
│ 세션 · 방송 상태 · 마지막 갱신 · 전체 준비도                  │
├ 입력 및 AI 상태 ──────────────────────────────────────────────┤
│ 캡처       오디오/자막       플랫폼 채팅       AI 모델/AI       │
│ 상태/최근성 상태/최근성      플랫폼별 상태     상태/대기 사유   │
├ 주요 토글 ────────────────────────────────────────────────────┤
│ AI 사용   채팅 수집   동의 안내(플랫폼별)   검토/공개 모드      │
├ 주요 제어 ────────────────────────────────────────────────────┤
│ 전체 준비 확인   필수 입력 시작   필수 입력 중지   AI 시작/중지   │
├ 원인 및 다음 조치 ────────────────────────────────────────────┤
│ 시작 불가 이유, 권한·설정 누락, 입력 지연, 오류별 해결 방법     │
└───────────────────────────────────────────────────────────────┘
아래: 페르소나 스튜디오 · 상세 설정 · 사용량 및 로그
```

화면이 좁으면 상태 카드를 여러 행으로 재배치할 수 있지만 위에서 아래로 읽는 정보 우선순위는 유지한다. AI 긴급 중지 제어는 스크롤이나 모달에 가리지 않도록 상단 고정 영역 또는 눈에 띄는 대시보드 위치에 둔다.

가림 영역 확인 기능은 제거되었다. 영상 준비도는 최근 프레임 수신으로 판단하며, 확인 버튼·`capture.confirmed` 상태·`POST /api/admin/capture/confirm` API는 제공하지 않는다. 빈 `capture.masks`를 지원하고 기존에 명시한 사각형만 선택적으로 적용한다. 플랫폼 채팅의 동의·철회 처리와는 별개다.

## 기본 표시와 상세 정보

정상일 때 상단에는 송출 화면·실제 채팅·음성 인식·AI 모델이 `정상`인지 간결하게 표시한다. 정상 플랫폼 목록, `connecting` 같은 내부 상태 코드, 수신 횟수, 프레임 나이, 요청 수, 모델명·내부 생성 단계는 기본 화면에 나열하지 않는다. 채팅 준비/중지는 한 번만 안내하며, 실제 문제가 생긴 플랫폼에 한해 사용자에게 필요한 조치를 표시한다. 준비 중·미사용·알 수 없음은 정상으로 표시하지 않는다.

정체 공개·AI 사용 스위치·긴급 중지·입력 제어는 항상 운영 영역에 둔다. 최신 영상과 인식된 자막도 유지한다. 기존 연결 카드와 모델 진단 정보는 기본 닫힘인 `연결 및 AI 상세 설정` 안에 둔다. 상단의 관련 링크를 누르면 해당 상세 영역을 열어 제어로 이동한다. 아래 표의 세부 계측값은 상세 보기에서 제공하며, 정상 기본 화면에 모두 표시하라는 의미가 아니다.

각 상태는 색상만으로 전달하지 않는다. 텍스트 라벨 또는 아이콘 이름을 함께 제공한다. “초록색 점”만으로 정상 여부를 알게 해서는 안 된다.

## 4. 주요 토글과 제어

### 4.1 AI 생성

- AI 켜기/끄기를 명확한 단일 제어로 제공한다.
- AI 시작은 모든 필수 입력의 현재 준비 여부를 서버에서 다시 확인해야 한다. 브라우저가 전달한 준비 상태만 신뢰해서는 안 된다.
- 시작이 거부되면 누락 입력과 이유를 상단 대시보드에 표시한다.
- 중지는 대기 중 생성, 검토, 게시 후보를 취소하고 새 AI 응답이 나가지 않도록 한다.
- 서버 재시작만으로 AI가 자동 실행되지 않는다. 방송 종료 시 AI도 자동 중지된다.

### 4.2 필수 입력 일괄 제어

- 캡처, 오디오/자막, 활성화된 플랫폼 채팅 수신기를 하나의 입력 그룹으로 보여준다.
- `상태 확인`은 모든 입력의 설정 유효성, 연결 상태, 최근 데이터 시각을 한 번에 갱신한다.
- `필수 입력 시작`과 `필수 입력 중지`를 제공한다. 수신기 시작 일부만 성공하면 성공/실패 구성 요소를 각각 표시한다.
- 입력 중지는 AI 중지와 구분한다. 수집 중지가 AI 생성에 미치는 영향을 즉시 설명한다.
- 하나라도 필수 입력이 꺼져 있거나 최신 상태가 아니면 AI 시작을 허용하지 않는다. 선택적인 플랫폼이 비활성화된 경우는 필수 입력 미충족으로 취급하지 않는다.
- 제어 요청은 중복 클릭에 안전하고, 진행 중·성공·부분 실패·실패 상태를 제공한다.

### 4.3 플랫폼별 개인정보 안내

- YouTube·CHZZK·SOOP 토글을 각각 제공한다. 하나의 전역 토글로 대체하지 않는다.
- 기본값은 꺼짐이다. 플랫폼 심사를 완료하고 해당 채널에서 사용할 수 있음을 운영자가 확인한 뒤에만 켠다.
- 토글 라벨 옆에 심사 통과 확인이 선행 조건임을 표시한다. 앱은 심사 통과를 추정하거나 토글을 자동으로 켜지 않는다.
- 설정 변경은 명확한 확인 결과와 서버 응답을 반영하며, 새로고침·서버 재시작 후에도 유지된다.
- 토글을 꺼도 동의 전 채팅 차단은 유지한다. 토글은 안내 노출만 제어한다.

## 5. 시청자 동의 안내 및 개인정보 상태

1. 플랫폼이 제공한 시청자 ID, 플랫폼, 채널, 현재 스트림 세션 기준으로 `!동의`와 `!철회`를 처리한다.
2. 동의 전 메시지 본문은 영구 저장, 공개 이벤트, 오버레이 메시지, AI·필터 모델 입력에 포함하지 않는다.
3. 플랫폼별 안내 토글이 켜져 있고 미동의 채팅이 관측되면 오버레이에 `!동의` 입력 시에만 화면에 표시된다는 안내를 보여준다. 안내에는 철회 방법 `!철회`도 포함한다.
4. 같은 플랫폼·채널에 대한 재안내 간격은 최소 30초다. 미동의 채팅이 계속 관측되면 쿨타임 이후 안내를 다시 표시한다.
5. `!철회`를 보낸 ID에는 해당 세션 동안 동의 안내를 다시 보내지 않는다. `!동의`와 `!철회` 명령 본문 자체는 일반 채팅으로 표시하거나 AI 입력에 넣지 않는다.
6. 철회 시 이미 노출되었던 해당 사용자의 메시지는 화면과 AI 컨텍스트에서 즉시 제거한다.
7. 동의 상태는 새 스트림 세션에 승계하지 않는다. 사용자 ID를 유지해야 하는 저장소에는 필요한 최소 정보만 보관하고, 안내 대상 추적에는 원문 대신 보호된 식별자를 쓴다.
8. 안내 UI는 채팅 수집이 사용자에게 직접 메시지를 발송한다고 오해하게 해서는 안 된다. 현재 플랫폼 발신 기능이 제공되지 않는 경우 안내는 앱 오버레이/리더에 표시된다고 명시한다.

## 6. 상호작용 및 접근성

- 상태 갱신 실패와 오래된 응답을 표시한다. 정상 상태에서 갱신 주기와 시각을 반복 노출하지 않는다. 갱신 실패 시 이전 값을 정상 상태처럼 유지하지 않는다.
- 시작·중지·토글은 키보드로 조작할 수 있고, 의미 있는 접근성 이름을 가진다.
- 준비 실패 요약은 화면 상단에서 찾을 수 있어야 하며, 각 원인에서 관련 제어 또는 설정으로 이동할 수 있어야 한다.
- 모바일 폭에서도 AI 긴급 중지와 전체 준비 요약을 찾을 수 있어야 한다.
- 값이 없는 필드는 예외를 발생시키지 않고 중립 상태를 표시한다. 예: `확인 불가`, `상태 응답이 오래됨`.
- 공개 리더/OBS 오버레이에는 관리자 설정, 내부 오류 상세, 플랫폼 사용자 식별자, AI 원본 표시 정보를 노출하지 않는다.

## 7. 데이터/API 계약

관리자 상태 응답은 대시보드가 한 번에 렌더링하는 데 필요한 다음 정보를 제공해야 한다.

- 세션 ID·종료 상태·응답 생성 시각
- 캡처/오디오/각 플랫폼 수신기 상태, 최근 입력 시각, 오류 요약
- AI 상태·단계·준비 점검 결과·모델 연결·호출/제한 상태
- 플랫폼별 동의 안내 토글의 유효값
- 대시보드 제어에 필요한 실행 가능 여부와 서버 판정 이유

응답의 필드는 버전 호환성을 고려한다. 선택 필드 부재가 프런트엔드 예외로 이어져 전체 대시보드를 가리면 안 된다. 서버는 제어 가능 여부를 재검증하고, 잘못된 플랫폼 키나 알 수 없는 설정은 거부한다. 설정 변경은 인증 및 CSRF/동일 출처 보호와 기존 변경 요청의 중복 방지 규칙을 따른다.

| ---------- | ------------------- | ----------------------------------------------------------------------------------------- |

| DASH-02    | 입력 준비도         | 캡처·오디오·모델 중 하나라도 미준비면 시작 차단 이유가 상단에 정확히 보인다.              |
| DASH-03    | 입력 일괄 제어      | 전체 입력 시작/중지와 상태 확인 후 구성 요소별 결과가 보인다.                             |
| DASH-04    | AI 제어             | AI 중지가 생성/검토/게시 대기를 취소하고 입력 수집 상태를 별도로 유지한다.                |
| DASH-05    | 서버 검증           | UI를 우회한 시작 요청도 서버에서 준비 상태를 다시 검사한다.                               |
| DASH-06    | 플랫폼 토글         | 세 플랫폼 토글이 독립적으로 바뀌고 재시작 후에도 유지된다.                                |
| CONSENT-01 | 기본 거부           | 동의 전 원문이 DB 메시지, 공개 이벤트, 화면, AI 요청에 나타나지 않는다.                   |
| CONSENT-02 | 동의/철회 명령      | 두 명령은 채팅/AI에 노출되지 않고 ID별 세션 상태만 갱신한다.                              |
| CONSENT-03 | 안내 및 쿨타임      | 활성 토글의 미동의 메시지에 안내하고, 30초 안에는 반복하지 않으며 쿨타임 이후 재안내한다. |
| CONSENT-04 | 철회 예외           | 철회한 ID는 반복 안내되지 않고 기존 메시지도 숨겨진다.                                    |
| CONSENT-05 | 플랫폼 격리         | 토글, 채널, 플랫폼, 스트림 세션 사이에 동의/안내 상태가 섞이지 않는다.                    |
| UI-01      | 불완전 상태 응답    | `setup`, 선택 필드 또는 플랫폼별 값이 없어도 관리자 화면 전체가 예외로 중단되지 않는다.   |
| UI-02      | 실제 브라우저 오류  | 관리자 첫 로드·새로고침·오래된 상태 응답에서 uncaught page error와 console error가 없다.  |
| UI-03      | 작은 화면/키보드    | 주요 상태와 긴급 중지에 모바일·키보드로 접근할 수 있다.                                   |

브라우저 인수 검증은 단위 테스트와 별도로 실행하고, 브라우저 런타임 오류 배열이 빈 상태를 확인한다. 브라우저 실행 환경이 없으면 이를 검증 통과로 기록하지 않고 차단 사유를 남긴다.

## 9. 변경 관리

- 대시보드의 첫 화면 배치, 개인정보 차단, 서버 측 준비 검사, AI 긴급 중지 의미를 바꾸는 변경은 이 문서와 인수 테스트를 함께 갱신한다.
- 새 시스템 토글은 소유 범위, 기본값, 재시작 지속성, AI 준비도와의 관계, 실패 시 동작을 문서화한다.
- 단순히 기존 화면 아래에 새 상태 카드를 추가하는 방식으로 대시보드 요구를 충족했다고 간주하지 않는다.
- 구현 완료 보고에는 관련 요구 ID와 실행한 검증 종류(빌드/단위/브라우저)를 구분해 기록한다.
